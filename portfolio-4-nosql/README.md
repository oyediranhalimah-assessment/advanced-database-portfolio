Portfolio 4: NoSQL and advanced data models for an event planning business.
I chose a document database (MongoDB) for KnH because it offers flexibility when storing information that could differ between events, while still modelling the same KnH case study as my PostgreSQL tables. For example, an event can have an optional guest_list field, which is only included when a client requires guest management; vendors could also have different fields depending on their services, such as menu options for a caterer and decoration options for a decor vendor. A vendor's services are stored inside the vendor document, while an event's guest list is stored inside the event document. In MongoDB Atlas, I created the knh_events database with two collections: vendors and events. I inserted two vendor documents and one event document, then searched for vendors by category using the { "category": "decoration" } filter, as demonstrated in mongodb-query-by-category.png.The inserted documents are saved as the .json files in the folder. One advantage of relational tables is that they support foreign keys,("venue": "Grand Royale Hall")  which can ensure that a booking refers to an existing venue, whereas a document database does not automatically enforce that relationship. Overall, MongoDB offers flexibility in how information is stored, while relational tables provide stronger relationship management and data integrity.
