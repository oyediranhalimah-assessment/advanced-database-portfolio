Portfolio 2: Query processing and optimisation for an event planning business
I did a query test ( SELECT * FROM events WHERE event_date = '2026-06-15' ) on the event table generated which was about 100,000 rows. Before creating an index, PostgreSQL used a sequential scan to read every row and discard 99,863 to return only the 143 matching events. The scan took 14 ms. Then i went ahead to create an index( event_date ) on the events table and it used a bitmap index scan and read 145 data pages instead of the initial 981 and it finished in 0.35 ms. This was about 40 times faster. The index is just for the database to look up date and jump straight to the correct rows instead of reading the entire table. It returned 143 rows both times. The downside is that the index must be updated alongside every added, changed or deleted event and this takes up space. As KnH business adds events, queries by date will get slower without an index which is why indexes matters.
